# picassobackend — документация серверной части

Серверная часть [PickUsAll (Picasso)](https://github.com/raaveinm/PickUsAll) — C++20 сервер на oat++ 1.3.0 для игровых дружеских компаний. Один инстанс является SSOT для тех бесед, которые на нём созданы; клиент держит по WS-соединению к каждому серверу, который он добавил.

Документ описывает **фактическое** состояние кода. Там, где что-то спроектировано, но не реализовано, это сказано явно. Продуктовый контекст и терминология (Artist / Palette / Color) живут в клиентском репозитории; здесь только сервер.

Смежные документы: [CLAUDE.md](../CLAUDE.md) — краткая выжимка с граблями сборки. [WEBRTC.md](WEBRTC.md) — требования к RTC-контуру и найденные пробелы в сигнальном протоколе.

---

## 1. Что сервер делает и чего не делает

**Делает:**

- Хранит историю сообщений. Postgres — источник истины, локальный Room у клиента — кэш.
- Маршрутизирует сигналинг RTC-звонков: определяет участников беседы, кто из них онлайн, и пересылает непрозрачные SDP/ICE-нагрузки по steamId.
- Проверяет OpenID-утверждения Steam при логине.

**Не делает:**

- Не касается медиа звонка. Аудио идёт P2P-мешем между участниками; SFU/микшера здесь нет и не планируется.
- Не ходит в Steam Web API за клиента — клиент делает это сам. Серверная задача только одна: проверить подпись Steam, чего клиент не может.

Обе временные заглушки явно помечены комментариями `TEMPORARY`/`TODO` в коде и существуют только чтобы прогнать сигналинг end-to-end до того, как шаги 3 (auth) и 4 (storage) дорожной карты будут закрыты.

Все настоящие заглушки (не временные реализации выше) отвечают **501** с текстом, называющим шаг дорожной карты, — вместо тихого возврата пустого значения. Пустая история читалась бы как «сообщений нет» и незаметно испортила бы клиентский кэш.

## 3. Быстрый старт

### Первичная настройка

Пресет `conan-release` появляется только после первого удачного `cmake`, поэтому на чистом клоне нужен прямой вызов:

```bash
cmake -S . -B build -G "Ninja Multi-Config" \
  -DCMAKE_C_COMPILER=/usr/bin/gcc-11 \
  -DCMAKE_CXX_COMPILER=/usr/bin/g++-11 \
  -DCMAKE_BUILD_TYPE=Release
```

`conan_conf.cmake` сам запускает `conan install` из репозиторного `.venv` и выводит профиль Conan из версии переданного компилятора.

### Сборка и запуск

```bash
cmake --build build --config Release
./build/Release/PickUsAllBackend
```

> **Используйте `--config`, а не сборочный пресет.** В пресете `conan-release`, который генерирует Conan, конфигурация не задана, поэтому при Ninja Multi-Config `cmake --build --preset conan-release` соберёт **Debug** и оставит `build/Release/PickUsAllBackend` устаревшим. Имя пресета говорит release, результат — нет.

### Переменные окружения

| Переменная | По умолчанию | Состояние |
|---|---|---|
| `PICASSO_BIND` | `0.0.0.0` | применяется |
| `PICASSO_PORT` | `8000` | применяется |
| `PICASSO_DB_DSN` | пусто | доходит до репозиториев, но они пока не подключаются |
| `PICASSO_PUBLIC_URL` | `http://127.0.0.1:8000` | доходит до `OpenIdVerifier`, но он пока не используется |
| `PICASSO_LOG_LEVEL` | `info` | **читается и игнорируется** |

`PICASSO_PORT` вне диапазона `1..65535` — это ошибка развёртывания, поэтому парсер бросает исключение, а не откатывается к умолчанию: молчаливый запуск не на том порту хуже, чем отказ стартовать.

`PICASSO_PUBLIC_URL` не выводится из адреса привязки намеренно — Steam OpenID требует, чтобы `realm`/`return_to` совпадали с тем, что видел браузер пользователя.

### Проверка

```bash
curl -i http://127.0.0.1:8000/ping     # 200, "pong", X-Service-Status: Healthy
curl -i http://127.0.0.1:8000/         # 200, static/index.html

PICASSO_PORT=8099 ./build/Release/PickUsAllBackend
```

## 4. Карта модулей

Восемь модулей, у каждого свой `CMakeLists.txt` с одной статической библиотекой. `src/CMakeLists.txt` собирает их в интерфейсный таргет `picasso_core`, который линкует исполняемый файл.

### 4.1 Направление зависимостей

```
transport ──▶ service ──▶ domain/ports ◀── storage
                            ▲
                            └── всё остальное тоже
```

`domain` не зависит ни от чего, кроме `picasso_base` (корень включений и уровень языка). Это правило держится не на code review, а на `target_link_libraries`: слой, потянувшийся вбок, не слинкуется.

Конкретно:

- `picasso_domain` не линкует ни oat++, ни драйвер, ни сокеты.
- `picasso_service` не линкует ни oat++, ни классы `Pg*`.
- `oatpp-postgresql` подключён к `picasso_storage` как `PRIVATE` — драйвер останавливается на этом таргете.

### 4.2 Таблица модулей

| Каталог | Таргет | Точка входа | Зависит от |
|---|---|---|---|
| [`domain/`](../src/domain) | `picasso_domain` | — (типы и порты) | `picasso_base` |
| [`dto/`](../src/dto) | `picasso_dto` | `Envelope.hpp` | domain, oatpp |
| [`storage/`](../src/storage) | `picasso_storage` | `makeRepositories(dsn)` | domain, *(private)* oatpp-postgresql |
| [`steam/`](../src/steam) | `picasso_steam` | `OpenIdVerifier` | domain |
| [`service/`](../src/service) | `picasso_service` | `makeServices(...)` | domain, steam, storage |
| [`transport/http/`](../src/transport/http) | `picasso_transport_http` | `registerControllers(...)` | dto, service, oatpp |
| [`transport/ws/`](../src/transport/ws) | `picasso_transport_ws` | `registerWsEndpoint(...)` | dto, service, oatpp-websocket |
| [`app/`](../src/app) | `picasso_app` | `picasso::app::run()` | всё вышеперечисленное |

### 4.3 `domain/` — ядро

Обычный C++: ни oat++, ни SQL, ни сокетов. Это та часть, которую можно тестировать без сервера и базы.

**Идентификаторы** ([`Ids.hpp`](../src/domain/Ids.hpp)) — не typedef'ы, а различимые типы через шаблон `Id<Tag, T>`. В сигнатурах несколько идентификаторов подряд (`relayToPeer(from, conversationId, to)`), и простой псевдоним позволил бы молча переставить их местами.

| Тип | Носитель |
|---|---|
| `SteamId` | `std::uint64_t` |
| `ConversationId` | `std::int64_t` |
| `MessageId` | `std::int64_t` |

**Сущности:** `Message`, `Conversation`, `Session`. Все временные метки — `std::int64_t`, epoch в миллисекундах, что совпадает с колонками `bigint` в схеме: конвертировать между типом времени БД и значением на проводе не нужно нигде.

**Порты** ([`domain/ports/`](../src/domain/ports)) — абстрактные интерфейсы, те самые швы между слоями:

| Порт | Методы | Кто реализует |
|---|---|---|
| `ChatRepository` | `append`, `historyAfter` | `PgChatRepository` |
| `ConversationRepository` | `isMember`, `members`, `conversationsOf` | `PgConversationRepository` |
| `SessionRepository` | `store`, `findByTokenHash`, `revoke` | `PgSessionRepository` |
| `PresenceRegistry` | `isOnline`, `onlineAmong` | `ConnectionHub` |
| `SignalTransport` | `sendTo`, `sendToAll` | `ConnectionHub` |

Два последних реализованы слоем **выше** — в `transport/ws`. Это не небрежность, а причина двухфазной сборки графа (см. §5).

В `SignalTransport` кадр — непрозрачная строка, а не DTO: `domain` не должен знать про oat++ и JSON. Кодирование живёт в `EnvelopeCodec`, сервисы решают только, кому что доставить.

### 4.4 `dto/` — контракт провода

Типы oat++ с макросами `DTO_FIELD`. Единственное место, где кодовая база встречается с форматом сериализации.

`MessageType` — обычный `enum class` со свободными функциями `parseMessageType` / `toWireString`. Не макрос `ENUM(...)` из oat++, потому что тип должен быть доступен слоям, которые oat++ не линкуют. `parseMessageType` для нераспознанного значения возвращает `Unknown` и никогда не бросает.

### 4.5 `storage/` — единственное место, где живёт SQL

`makeRepositories(dsn)` конструирует три репозитория. Конструирование дёшево и в сеть не ходит, поэтому остальной процесс можно собрать до того, как база вообще появится — заглушки бросают только при реальном вызове метода.

`migrate(dsn)` должен применять [`migrations/0001_init.sql`](../src/storage/migrations/0001_init.sql). Не реализован, файл существует, никто его не применяет.

### 4.6 `steam/` — единственная задача, обращённая к Steam

`OpenIdVerifier` строит URL логина и отправляет утверждение обратно на `steamcommunity` с `mode=check_authentication`. `verify()` возвращает steamId, только если Steam подтвердил. `std::nullopt` означал бы «подделано, воспроизведено или испорчено» — все три случая неразличимы и одинаково отвергаются.

Заглушка бросает, а не возвращает `nullopt`: тихий «отказ логина» неотличим от настоящего.

### 4.7 `service/` — сценарии использования

| Сервис | Ответственность | Состояние |
|---|---|---|
| `ChatService` | `submit(sender, conversationId, localMessageId, body)` — проверить членство, записать, подтвердить, разослать | заглушка, 501 (шаг 4) |
| `CallSignalService` | `invite(...)` — уведомить онлайн-участников беседы о начале звонка; `relayToPeer(...)` — проверка членства и пересылка | `invite()` — заглушка, 501; `relayToPeer()` — **реализован**, но временно без проверки членства (открытый relay), см. §2 |
| `AuthService` | `beginLoginUrl()`, `completeLogin(params)`, `authenticate(token)` | `beginLoginUrl`/`completeLogin` — заглушки, 501; `authenticate()` — **реализован временно**: bearer-токен = steamId без проверки |

`makeServices` принимает `PresenceRegistry` и `SignalTransport` аргументами, а не создаёт их: оба реализует `ConnectionHub` из слоя выше.

Методы `AuthService` объявлены `static` (включая уже работающий `authenticate`) — временно это компилируется, потому что временная реализация не трогает `sessions_`/`verifier_`, но на шаге 3 их придётся вернуть в нестатические.

Порядок в `ChatService::submit` задан: сначала запись, потом подтверждение, потом рассылка. Подтверждение не должно обещать сохранность, которую база ещё не подтвердила.

### 4.8 `transport/http/` — REST

Контроллеры плюс `ErrorHandler`. `registerControllers` — единственное место, куда добавляется контроллер; композиционный корень не знает, сколько их.

### 4.9 `transport/ws/` — чат и сигналинг

| Файл | Роль |
|---|---|
| `WsController` | эндпоинт апгрейда; **здесь и только здесь** соединение получает личность |
| `WsModule` | `SessionFactory` — мост между жизненным циклом сокета oat++ и нашим |
| `WsSession` | одно подключение; слушатель oat++ и реализация `Outbound` |
| `ConnectionHub` | `SteamId → набор соединений`; реализует два доменных порта |
| `EnvelopeCodec` | кадр ↔ `EnvelopeDto`, единственная точка отбраковки мусора |
| `Outbound` | то, что хабу разрешено делать с соединением |

`ConnectionHub` намеренно не содержит типов oat++, хотя лежит в транспорте: он общается с сессиями через `Outbound`, поэтому логику присутствия и рассылки можно тестировать без сокета.

Один `SteamId` отображается в **несколько** соединений: клиент, открытый на телефоне и на десктопе, — это два соединения, и получить должны оба.

### 4.10 `app/` — композиционный корень

Единственный модуль, которому позволено знать обо всех остальных.

| Файл | Роль |
|---|---|
| `Config` | чтение `PICASSO_*` |
| `Components` | всё, чем процесс владеет всю жизнь, в одной структуре |
| `App` | `buildComponents` + `run()`; владеет временем жизни `oatpp::base::Environment` |
| `ServerRunner` | привязка с внятной ошибкой, установка обработчика ошибок, `server.run()` |

`main.cpp` — одна строка. Это не косметика: тестовый бинарь может собрать тот же граф, не проходя через точку входа процесса.

## 5. Порядок сборки графа

Порядок в `buildComponents` — следствие слоёв, а не предпочтение:

```
ObjectMapper, HttpRouter
        │
        ▼
  Repositories            (makeRepositories — в сеть не ходит)
        │
        ▼
  ConnectionHub           ← должен существовать до сервисов:
        │                   он и есть их PresenceRegistry и SignalTransport
        ▼
  Services                ← должны существовать до WS-эндпоинта:
        │                   сессии вызывают их
        ├──▶ http::registerControllers(router, mapper, services)
        └──▶ ws::registerWsEndpoint(router, mapper, hub, services)
```

Двухфазность здесь неизбежна. Хаб находится над сервисами по слоям, но реализует их порты — разорвать цикл можно только передачей через аргументы.

`Components` хранится по значению в `run()`, поэтому порядок разрушения обратен порядку создания и ничто не переживает то, на что ссылается.

## 6. REST-эндпоинты

Все ответы, кроме успешных, имеют один формат (`ErrorDto`):

```json
{ "status": 501, "code": "Not Implemented", "message": "…" }
```

### `GET /ping`

Проверка живости. Реализовано.

```
200 OK
Content-Type: text/plain; charset=utf-8
X-Service-Status: Healthy

pong
```

### `GET /`

Отдаёт `static/index.html`. Реализовано. `404`, если файла нет.

Путь зашит на этапе компиляции через `PICASSO_STATIC_ROOT` и указывает в дерево исходников — контейнеризацию это не переживёт.

### `GET /auth/steam/begin`

Начало логина. Должен отдавать `302` с заголовком `Location` на Steam.

Сейчас: **501**, `AuthService::beginLoginUrl`.

> В oat++ 1.3.0 у `Header` нет константы `LOCATION` — только `CONTENT_TYPE`, `AUTHORIZATION` и ещё несколько. Используется литерал `"Location"`.

### `GET /auth/steam/return`

Steam возвращает пользователя сюда с утверждением в query-строке. Все параметры `openid.*` собираются целиком и передаются в `check_authentication` дословно — разбирать их нельзя, подпись считается по всему набору.

Успех вернёт `AuthTokenDto`:

```json
{ "token": "…", "steamId": "7656119…", "expiresAt": 1788952742266 }
```

`token` — открытый текст, отдаётся клиенту ровно один раз. В базе лежит только его SHA-256.

Сейчас: **501**, `AuthService::completeLogin`. Отклонённое утверждение даст `401`.

### `GET /conversations/{conversationId}/messages`

Синхронизация клиентского кэша — то, ради чего сервер объявлен SSOT.

| Параметр | Где | По умолчанию | Смысл |
|---|---|---|---|
| `conversationId` | path | — | беседа |
| `after` | query | `""` | последний известный клиенту `messageId`; пусто — с начала |
| `limit` | query | `100` | размер страницы |

Ответ — `MessagePageDto`: список `ChatMessageOutDto` и `nextAfter`. `nextAfter` равный `null` означает, что клиент догнал сервер.

Сейчас: **501**, шаг 4.

### `GET /ws`

Апгрейд до WebSocket. Разобран в §7.

## 7. WebSocket

### 7.1 Апгрейд и получение личности

Одно соединение на клиента на сервер, несущее **и** чат, **и** сигналинг RTC.

```
GET /ws
Authorization: Bearer <token>
```

Клиент — KMP-приложение, а не браузер, поэтому заголовки на запросе апгрейда доступны, и обходные пути с query-параметром или одноразовым тикетом не нужны.

| Условие | Ответ |
|---|---|
| нет заголовка `Authorization` | `401` `missing bearer token` |
| токен не парсится как целое число (`std::stoull` бросает) | `401` `invalid or expired token` |
| токен — произвольное число | **успех**, `101 Switching Protocols` — число трактуется как steamId без проверки (временная реализация, см. §2) |

Раньше здесь стоял 501 (заглушка `authenticate`); теперь `authenticate()` реально работает, просто небезопасно. Настоящая проверка Steam OpenID (шаг 3) ещё не написана — см. предупреждение в §2.

Проверенный `steamId` передаётся сессии **через параметры апгрейда** (`ParameterMap`), а не через что-либо, что клиент может прислать позже. `SessionFactory::onAfterCreate` читает его оттуда; сокет без steamId немедленно закрывается — попасть туда можно, только маршрутизировав соединение в обход `WsController`.

### 7.2 Формат кадра

Каждый кадр в обе стороны — `EnvelopeDto`. Поле `type` определяет, какое поле нагрузки заполнено.

```json
{
  "type": "chat_message",
  "chatMessage": { "conversationId": "12", "localMessageId": "a1b2", "body": "hi" }
}
```

| `type` | Поле нагрузки | Направление | Смысл | Обработка в `dispatch` сейчас |
|---|---|---|---|---|
| `chat_message` | `chatMessage` (`ChatMessageInDto`) | клиент → сервер | новое сообщение | только лог, `ChatService::submit` не вызывается (бросает) |
| `chat_ack` | `chatAck` (`ChatAckDto`) | сервер → отправителю | «сообщение записано» | не производится — зависит от `chat_message` |
| `call_invite` | `callInvite` (`CallInviteDto`) | клиент → сервер | начать/войти в звонок | только лог, `CallSignalService::invite` не вызывается (бросает) |
| `incoming_call`, `call_accept`, `call_decline`, `peer_joined`, `call_leave` | `callSignal` (`CallSignalDto`) | обе | уведомления `{conversationId, steamId}` | попадают в `default:`, лог «unhandled frame type» |
| `sdp_offer`, `sdp_answer` | `sdp` (`SdpDto`) | обе, по `toSteamId` | непрозрачный SDP | **пересылается** через `CallSignalService::relayToPeer`, `fromSteamId` проставляется сервером |
| `ice_candidate` | `iceCandidate` (`IceCandidateDto`) | обе, по `toSteamId` | непрозрачный ICE-кандидат | **пересылается**, `fromSteamId` проставляется сервером |
| `call_hangup` | `callHangup` (`CallHangupDto`) | обе, по `toSteamId` | сигнал «повесить трубку», собственной нагрузки кроме адресации нет | **пересылается**, `fromSteamId` проставляется сервером |

Нераспознанный `type` кадр отбрасывается с записью в лог, соединение не рвётся.

`EnvelopeDto` также несёт поле `chatMessageOut` (`ChatMessageOutDto`), которому не соответствует ни один wire-`type` — задел на момент, когда `ChatService` начнёт рассылать сообщение остальным участникам беседы. Сейчас нигде не заполняется и не читается.

### 7.3 Полезные нагрузки

**`ChatMessageInDto`** — `conversationId`, `localMessageId`, `body`.

Поля отправителя **нет**. Это не упущение: сервер выводит отправителя из аутентифицированного соединения, и поле, присланное клиентом, пришлось бы либо игнорировать, либо доверять ему. Отсутствие поля — единственная форма, где нечего игнорировать.

**`ChatMessageOutDto`** — `conversationId`, `messageId`, `senderSteamId`, `body`, `createdAt`. Отправитель и идентификатор проставлены сервером.

**`ChatAckDto`** — `conversationId`, `localMessageId`, `messageId`.

Несёт и эхо `localMessageId`, чтобы клиент закрыл свою `PENDING`-строку, и серверный `messageId`, чтобы он знал, где теперь заканчивается его кэш. Без второго синхронизация через `?after=` нереализуема.

**`SdpDto`** / **`IceCandidateDto`** — `conversationId`, `toSteamId`, `fromSteamId`, плюс `sdp` или `candidate`.

`fromSteamId` проставляет сервер на исходящем пути; присланный клиентом отбрасывается. `sdp` и `candidate` сервер не разбирает никогда.

**`CallHangupDto`** — `conversationId`, `toSteamId`, `fromSteamId`. Адресуется так же, как `SdpDto`/`IceCandidateDto`, но своей полезной нагрузки не несёт — сам факт кадра и есть сигнал.

### 7.4 Что происходит с кадром сейчас

`WsSession::readMessage` накапливает фрагменты (кадр завершён, когда oat++ вызывает метод с `size == 0`), затем `dispatch` декодирует конверт и разбирает `type`. Дальше поведение расходится по типу:

- **`sdp_offer` / `sdp_answer` / `ice_candidate` / `call_hangup`** — реально пересылаются. `dispatch` разбирает `toSteamId` и `conversationId` из нагрузки (кадр с нераспознаваемыми полями молча отбрасывается с логом), перезаписывает `fromSteamId` значением текущей сессии, пересобирает конверт через `EnvelopeCodec::envelopeOf` и зовёт `CallSignalService::relayToPeer(steamId_, conversationId, to, encoded)`. Это первый путь в коде, где `dispatch` действительно вызывает сервис, а не только логирует.
- **`chat_message` / `call_invite`** — разбираются и **пишутся в лог**, сервис не вызывается (оба всё ещё бросают: `ChatService::submit`, `CallSignalService::invite`).
- **остальные типы** (`incoming_call`, `call_accept`, `call_decline`, `peer_joined`, `call_leave`) — попадают в `default:`, тоже только лог.

Исключение из сервиса ловится и логируется, а не рвёт соединение — это касается и `relayToPeer`, хотя сейчас он не бросает в штатных условиях (открытый relay, см. §2, ничего не проверяет и не отклоняет).

## 8. Модель ошибок

Единственный формат ответа при неуспехе — `ErrorDto`. Реальные примеры:

```json
{"status":401,"code":"Unauthorized","message":"missing bearer token"}
{"status":404,"code":"Not Found","message":"No mapping for HTTP-method: 'GET', URL: '/nope'"}
{"status":501,"code":"Not Implemented","message":"service: AuthService::authenticate is not implemented yet (roadmap step 3: auth)"}
```

### Как получается 501

Здесь есть неочевидная деталь, продиктованная версией oat++.

В `oatpp/1.3.0` (тегированный релиз) у `ErrorHandler` есть **только** чистый виртуальный `handleError(status, message, headers)`. Перегрузки `handleError(const std::exception_ptr&)` нет — она существует лишь в ветке `1.3.0.latest`. `HttpProcessor` сам ловит `std::exception` и передаёт обработчику уже готовый `500`. Тип исключения до нас не доходит.

Поэтому единственный оставшийся канал — префикс в тексте сообщения. [`domain/Errors.hpp`](../src/domain/Errors.hpp) определяет `kNotImplementedPrefix`, все заглушки бросают через общий `notImplemented(what, step)`, а `ErrorHandler` поднимает статус до `501` и срезает префикс.

Проверено, что механизм не срабатывает лишний раз: настоящий 404 остаётся 404, `401` от `OATPP_ASSERT_HTTP` остаётся 401.

## 9. Схема базы данных

Живёт в [`0001_init.sql`](../src/storage/migrations/0001_init.sql). Никем не применяется. Диаграмма для chartdb — [`schema.chartdb.json`](schema.chartdb.json), но **авторитетен именно SQL**: часть ограничений в формате диаграммы невыразима, см. §9.3.

```
users        (steam_id PK)
sessions     (token_hash PK, steam_id → users, created_at, expires_at, revoked_at)

conversations (id identity PK, kind CHECK ('dm'|'palette'), created_at, UNIQUE(id, kind))
  ├── chat    (conversation_id PK → conversations, member_a → users, member_b → users)
  └── palette (conversation_id PK → conversations, name)
                 └── members (palette_id → palette, user_id → users, joined_at)
                             PK(palette_id, user_id)

message_data (id identity PK, conversation_id → conversations,
              sender_steam_id → users, text_message, sent_at)

game_queue   (id identity PK, user_id → users, game_id, priority, enqueued_at,
              UNIQUE(user_id, game_id))
```

Все идентификаторы и метки времени — `bigint`; время в миллисекундах epoch, что совпадает с доменными структурами (`Message::createdAtEpochMs`), поэтому конвертировать между типом времени БД и значением на проводе не нужно нигде. `ConversationId` в домене — `int64`, а не строка.

Имена колонок в snake_case и без кавычек намеренно: Postgres сворачивает неэкранированные идентификаторы в нижний регистр, поэтому колонку, созданную как `"steamId"`, придётся цитировать в каждом запросе навсегда.

### 9.1 Две специализации беседы

`conversations` — супертип, `chat` и `palette` — две непересекающиеся специализации. DM это ровно двое, и это обеспечено тем, что колонок ровно две; Palette это группа, и участники лежат в отдельной таблице.

`UNIQUE (id, kind)` в `conversations` выглядит избыточным рядом с первичным ключом, но именно он позволяет специализациям ключеваться по `(conversation_id, kind)`. Колонка `kind` в `chat` и `palette` — генерируемая константа (`GENERATED ALWAYS AS ('dm') STORED`), которая скармливается составному внешнему ключу. В результате «беседа — либо dm, либо palette, но не оба сразу» становится ограничением, а не соглашением.

Цена разделения: «в каких беседах состоит пользователь» и «состоит ли пользователь в беседе» превращаются в двухветочные запросы (UNION по `chat` и `members`). Порты домена этого не замечают — `ConversationRepository` оперирует `isMember`/`members`/`conversationsOf`, а UNION поглощает репозиторий.

### 9.2 Решения, которые не стоит пересматривать

**Нет колонки `role` в `members`.** Внутри Palette все участники — равноправные владельцы, различать нечего. Добавить позже — это миграция; поддерживать модель прав, которой не существует, — мёртвый груз.

**Первичный ключ `members` — пара `(palette_id, user_id)`.** Ключ по одному `palette_id` ограничил бы Palette одним участником, что прямо противоположно смыслу дружеской группы.

**`message_data.id` — первичный ключ сам по себе**, глобальный и монотонный, плюс индекс по `(conversation_id, id)`. Составной ключ `(id, conversation_id)` не гарантировал бы уникальность `id` в одиночку, а контракт синхронизации `?after={id}` держится именно на ней. Отдельный индекс нужен потому, что индекс по одному `id` не отвечает на запрос «эта беседа, после N».

Сообщения висят на `conversations`, а не на `chat` или `palette`, поэтому история работает одинаково для DM и для Palette.

**`sessions` — отдельная таблица, а не колонка в `users`.** Одна строка на пользователя ограничила бы его одной живой сессией, а `ConnectionHub` намеренно отображает один steamId в несколько сокетов (телефон и десктоп одновременно). И хеш не помещается в `bigint`: SHA-256 это 256 бит, обрезка до 64 убивает стойкость к коллизиям.

**`token_hash`, а не `token`.** Открытый текст отдаётся клиенту один раз при логине и не сохраняется, поэтому дамп базы — не набор живых сессий. `expires_at` отделён от `revoked_at`: истечение автоматическое, отзыв — явный выход.

**`CHECK (member_a < member_b)` в `chat`** делает две вещи сразу: исключает беседу с самим собой и задаёт единственный канонический порядок пары, благодаря чему `UNIQUE (member_a, member_b)` действительно предотвращает второй DM между теми же людьми, а не обходится вставкой в обратном порядке.

**Индексы на `chat(member_a)` и `chat(member_b)`.** Запрос «мои беседы» идёт на каждом подключении WS; без них это последовательное сканирование всех DM на сервере.

### 9.3 Чего не видно на диаграмме

Формат chartdb не выражает генерируемые колонки, `CHECK`-ограничения и составные внешние ключи. Значит, на диаграмме отсутствуют:

- `kind GENERATED ALWAYS AS (...) STORED` в `chat` и `palette` — показаны как обычные колонки;
- составной внешний ключ `(conversation_id, kind) → conversations (id, kind)` — показан как связь только по `conversation_id`;
- `CHECK (member_a < member_b)` и `CHECK (kind IN ('dm','palette'))`;
- `UNIQUE (id, kind)` в `conversations`.

То есть SQL, сгенерированный обратно из диаграммы, будет слабее файла миграции. Диаграмма годится для обзора связей, но источником истины остаётся `0001_init.sql`.

### 9.4 `game_queue`

Новая сущность, серверного кода под неё пока нет: ни порта в `domain/ports`, ни сервиса, ни эндпоинта. `game_id` — это appid Steam, непрозрачное число, таблицы игр для джойна нет.

`enqueued_at` нужен, чтобы у записей с одинаковым `priority` был определённый порядок — без него вопрос «кто ждёт дольше всех» не имеет ответа. `UNIQUE (user_id, game_id)` не даёт одному пользователю встать в очередь на одну игру дважды.

## 10. Инварианты

Первый обеспечен структурно уже сейчас, хоть и опирается на временную (небезопасную) аутентификацию. Пересылка SDP/ICE реализована в коде, но **без** проверки членства — инвариант описывает целевое поведение, которого сегодняшний код не исполняет. Третий — намерение, под которое каркас сформирован, но которое пока не исполняется кодом.

### `senderSteamId` берётся из соединения, никогда из нагрузки

Обеспечено разделением входящих и исходящих DTO. У `ChatMessageInDto` нет поля отправителя вообще — доверять нечему. `ChatService::submit(SteamId sender, …)` принимает отправителя параметром, и единственный, кто может его назвать, — `WsSession`, которому личность вбита в конструктор после проверки токена при апгрейде. Пропустить проверку не получится: код без неё не соберётся.

Оговорка: структурная гарантия держится на том, что личность соединения *в принципе* проверена при апгрейде — а сегодня эта проверка (`AuthService::authenticate`) сама временная и ничего не удостоверяет, кроме того что токен — число. Инвариант «откуда берётся `senderSteamId`» соблюдён; вопрос «а можно ли доверять этому `senderSteamId`» пока нет.

### Пересылка SDP/ICE проверяется на членство — **пока не в этой сборке**

«Пересылать по `toSteamId`, не разбирая» в буквальном прочтении делает сервер открытым релеем: любой аутентифицированный пользователь смог бы слать произвольные нагрузки любому steamId в обход членства в беседе. `CallSignalService` обязан убедиться, что и отправитель, и получатель состоят в `conversationId`, прежде чем пересылать.

Сегодня `CallSignalService::relayToPeer` этого не делает — пересылает всё, что получит, без единой проверки. Это отмечено `TODO(roadmap step 4/5)` прямо в `CallSignalService.cpp`: проверка ждёт, пока `ConversationRepository` станет настоящим (шаг 4), а не заглушкой. До тех пор сервер — буквально открытый relay по `toSteamId`. См. предупреждение в §2 и [WEBRTC.md §3.6, §7.6](WEBRTC.md).

ICE-кандидаты приходят пачками, поэтому *когда* проверка появится, набор бесед пользователя должен кэшироваться на сессии при подключении, а не запрашиваться на каждый кандидат — это архитектурное требование, не то, что уже сделано.

### Один писатель на сокет

Рассылка идёт в потоке чужого соединения, а блокирующий `sendOneFrameText` не безопасен при конкурентном вызове на одном сокете.

Сейчас: `WsSession` сериализует отправку мьютексом. Конкурентные отправки безопасны, но backpressure нет — медленный потребитель блокирует того, кто ему рассылает. Задумано: ограниченная очередь с единственным писателем.

Политика сброса при переполнении имеет **три** яруса, а не два: чат не роняется никогда (сервер — SSOT), управление звонком и SDP не роняются никогда (потеря `sdp_offer` молча ломает установку сессии, и повтора не будет), и ронять допустимо только `ice_candidate` — кандидатов много, они частично избыточны и продолжают приходить. Разбор в [WEBRTC.md](WEBRTC.md) §4.3.

### Присутствие не требует внешнего хранилища

Мультисерверный дизайн делает присутствие локальным для инстанса по построению: клиент держит по соединению к каждому серверу, поэтому «онлайн» всегда значит «онлайн здесь». Redis не нужен.

## 11. Модель конкурентности

Используется **блокирующий** API oat++: `oatpp::network::Server` + `HttpConnectionHandler`, то есть поток на соединение, а с долгоживущими WS — поток на клиента.

Выбор осознанный. Palette — конструкт дружеской компании, а не публичная комната; Free Tier целится в небольшой VPS. Реальная нагрузка — десятки, максимум пара сотен одновременных соединений.

Асинхронный API (`AsyncHttpConnectionHandler` + `AsyncWebSocket`) масштабируется дальше, но отравляет цикл событий на любом блокирующем вызове, а пул `oatpp-postgresql` блокирующий — работу с БД пришлось бы уводить в отдельную executor-группу.

**Требование локализации:** модель конкурентности должна оставаться внутри `ws/ConnectionHub` и `ws/WsSession`, чтобы возможная миграция не расползлась по коду.

`ConnectionHub` собирает живые соединения под разделяемой блокировкой и **освобождает её до отправки**. Запись в сокет под блокировкой хаба выстроила бы всю рассылку в процессе за самым медленным потребителем, а заблокировавшаяся отправка держала бы реестр в заложниках.

Стоит уменьшить размер стека потоков: 8 МБ по умолчанию, умноженные на пару сотен соединений, — впустую занятая память на маленькой машине. Пока не сделано.

## 13. Что не сделано

> Текущий билд включает две **временные, явно небезопасные** заглушки, добавленные ради сквозного теста сигналинга — не путать с «реализовано»:
> - `AuthService::authenticate` принимает bearer-токен как готовый steamId без проверки подписи.
> - `CallSignalService::relayToPeer` пересылает кадры без проверки членства в беседе (открытый relay).
>
> Обе помечены `TEMPORARY`/`TODO` прямо в исходниках и не предназначены для публичного развёртывания.

- **Ничего не сохраняется.** Драйвер подключён, SQL написан, но ни один заголовок драйвера не включён: все методы репозиториев бросают, `migrate` не применяет миграцию.
- **Нет настоящей аутентификации.** `OpenIdVerifier` и `AuthService::beginLoginUrl`/`completeLogin` — заглушки. `AuthService::authenticate` больше не заглушка — он реально пропускает соединение в `/ws`, но не проверяет вообще ничего, кроме того, что токен — целое число (см. предупреждение выше). Инвариант `senderSteamId`, будучи структурно на месте, теперь и правда отрабатывает — но на непроверенной личности.
- **Пересылка RTC — открытый relay.** `CallSignalService::relayToPeer` реализован и реально пересылает `sdp_offer`/`sdp_answer`/`ice_candidate`/`call_hangup`, но без проверки, что отправитель и получатель состоят в `conversationId`. `CallSignalService::invite` по-прежнему заглушка.
- **Кадры чата разбираются, но не обрабатываются.** `chat_message` и `call_invite` доходят до `switch` в `dispatch` и логируются — `ChatService::submit` и `CallSignalService::invite` не вызываются, оба бросают.
- **Нет backpressure** на исходящем пути сессии (см. §10).
- **Нет плавного завершения.** `server.run()` блокирует до убийства процесса; обработка SIGTERM названа в `ServerRunner`, но не написана.
- **Нет тестов.** `picasso_core` существует, чтобы их линковать; `domain/` и `ConnectionHub` написаны так, чтобы тестироваться без сервера, но не написано ничего.
- **`PICASSO_LOG_LEVEL` игнорируется.**
- **`static/` зашит на этапе компиляции** и указывает в дерево исходников.
- **Методы `AuthService` объявлены `static`**, включая уже рабочий `authenticate`. Пока временная реализация не трогает `sessions_`/`verifier_`, это компилируется, но `beginLoginUrl`/`completeLogin` обязаны будут обращаться к `verifier_`, а настоящий `authenticate` — к `sessions_`. На шаге 3 их придётся вернуть в нестатические.

## 14. Дорожная карта

Порядок ограничен, а не произволен: шаг 3 обязан предшествовать шагу 4, иначе первые же строки в `message_data` уедут с непроверенным отправителем. Шаг 5 идёт после 4, потому что членство берётся из базы.

1. ~~**Каркас** — `app/`, конфиг из окружения, внятная ошибка при отказе привязки, единый обработчик ошибок.~~ Сделано.
2. **WS-транспорт** — хаб, сессия и кодек есть; `dispatch` теперь вызывает `CallSignalService` для четырёх RTC-типов кадров, но `chat_message`/`call_invite` всё ещё только логируются, а ограниченная исходящая очередь не добавлена. Разблокирует клиента: `ChatRepository.sendToServer()` получит, к чему подключаться, как только чат будет проведён по тому же пути.
3. **Аутентификация** — Steam OpenID, токены сессий, проверка при апгрейде. Временная заглушка (`authenticate` = «bearer-токен есть steamId») уже разблокировала тестирование шага 5 — но именно поэтому шаг 3 ещё не закрыт: `senderSteamId` станет настоящим только после реальной проверки Steam OpenID.
4. **Хранение** — миграции, репозитории, `ChatService` начинает писать, REST-история.
5. **Сигналинг RTC** — проверка членства плюс пересылка. Пересылка (`relayToPeer`) уже реализована; проверка членства — нет, она ждёт настоящего `ConversationRepository` из шага 4. `invite()` тоже ещё не реализован.
