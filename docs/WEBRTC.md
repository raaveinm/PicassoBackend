# Требования к RTC-контуру picassobackend

Требования к голосовым звонкам, приведённые к специфике этого проекта. Общий шаблон требований к WebRTC исходит из связи «клиент A ↔ клиент B через комнату», а здесь топология другая, и почти все числовые оценки из-за этого меняются.

Что нужно держать в голове, читая документ:

| Общий шаблон                              | Здесь                                                                          |
|-------------------------------------------|--------------------------------------------------------------------------------|
| Пара пиров, сопоставление по Room ID      | **Полный P2P-меш** внутри Palette, участники берутся из `members` (для DM — из `chat`) |
| Отдельный сигнальный сокет                | Тот же WS, что несёт чат (`GET /ws`)                                           |
| Pass-through тела сообщения без изменений | **Пересылка с проверкой членства** — иначе сервер становится открытым релеем   |
| Один сервер                               | Мультисерверная схема: клиент держит по соединению к каждому серверу           |
| `offer` / `answer` / `ice-candidate`      | `EnvelopeDto` с полем `type`                                                   |

Текущее состояние сигналинга: `CallSignalService::relayToPeer` реализован и реально пересылает `sdp_offer`/`sdp_answer`/`ice_candidate`/`call_hangup` (последний — новый тип кадра, добавлен вместе с пересылкой), но **как открытый relay, без проверки членства** — TODO на это стоит прямо в коде и ждёт настоящего `ConversationRepository` (шаг 4 дорожной карты). `invite()` по-прежнему заглушка, отдаёт 501. Аутентификация `/ws`, от которой зависит вся пересылка, тоже временная: bearer-токен трактуется как steamId без проверки. **Ни то, ни другое не готово к продакшену** — обе заглушки существуют только чтобы прогнать протокол сигналинга end-to-end. См. [SERVER.md §2, §7, §10](SERVER.md) для фактического состояния протокола.

## 1. Топология и почему она определяет всё остальное

Медиа идёт полным мешем между участниками звонка. Сервер медиа не касается — ни микширования, ни SFU. Для беседы из **N** участников:

- каждый клиент держит **N−1** PeerConnection;
- всего в звонке **N(N−1)/2** соединений;
- каждый клиент кодирует **N−1** раз (в libwebrtc у каждого PeerConnection свой инстанс кодека, общий у них только источник звука) и декодирует **N−1** раз.

Это осознанный размен: меш — O(N²), что нормально для DM и небольшой Palette и непригодно для публичной комнаты. Palette и есть конструкт дружеской компании.

**Практическое следствие:** ни одну оценку «на один активный разговор» из общего шаблона нельзя брать как есть. Всё, что относится к клиенту и к TURN, умножается на N−1; всё, что относится к сигнальному серверу, — на N(N−1)/2.

## 2. Требования к клиенту

Реализация клиента живёт в репозитории [PickUsAll](https://github.com/raaveinm/PickUsAll). Здесь — только то, что сервер о клиенте предполагает.

### 2.1 Аудио-периферия

- Микрофон с частотой дискретизации не ниже 16 кГц, рекомендуется 48 кГц.
- Динамик или наушники.

### 2.2 Разрешения ОС

Клиент — KMP/Compose. Набор целевых платформ задаётся клиентским репозиторием; ниже — требования для тех, которые он собирает.

| Платформа                   | Требуется                                                                                      |
|-----------------------------|------------------------------------------------------------------------------------------------|
| Android                     | `android.permission.RECORD_AUDIO`, `android.permission.MODIFY_AUDIO_SETTINGS`                  |
| Desktop Linux               | доступ к PulseAudio / PipeWire                                                                 |
| Desktop Windows             | WASAPI                                                                                         |
| Desktop macOS               | CoreAudio                                                                                      |
| iOS *(если поддерживается)* | `NSMicrophoneUsageDescription` в `Info.plist`, категория `AVAudioSessionCategoryPlayAndRecord` |

Строку про iOS оставил условной намеренно: подтверждения, что клиент собирает iOS-таргет, у меня нет. Уточните по клиентскому репозиторию и уберите оговорку либо строку.

### 2.3 Кодек и DSP

- **Opus** — обязателен по RFC 7874. Для речи оптимально 16–32 kbps, моно.
- **G.711 (PCMA/PCMU)** — запасной вариант совместимости, 64 kbps.
- `useinbandfec=1` в SDP — включает FEC, за счёт которого Opus переживает 10–15% потерь.

DSP-модули критичны при работе без наушников, и в меше — сильнее, чем в связи один-на-один: эхо от **каждого** из N−1 удалённых голосов попадает обратно в микрофон.

- **AEC** — подавление акустического эха.
- **NS** — подавление фонового шума.
- **AGC** — авторегулировка уровня входа.
- **VAD** — детектор речевой активности.

VAD в меше даёт экономию, растущую с N: молчащий участник перестаёт слать N−1 потоков, а не один. В компании, где одновременно говорит один-два человека, это основной способ удержать полосу.

### 2.4 Конфигурация медиапайплайна

- Видео не инициализируется вообще, на уровне создания треков.
- Трансивер: `addTransceiver(AUDIO)` с направлением `SEND_RECV`.
- В SDP ровно одна секция `m=audio`, секции `m=video` быть не должно.

### 2.5 Масштабирование по числу участников

Полоса на клиента считается как (N−1) × поток. Один поток — Opus 24 kbps плюс оверхед UDP/IP/SRTP/RTCP, суммарно ≈32 kbps.

| N | PeerConnection на клиента | Соединений в звонке | Полоса ↑ и ↓ на клиента |
|---|---------------------------|---------------------|-------------------------|
| 2 | 1                         | 1                   | ≈32 kbps                |
| 3 | 2                         | 3                   | ≈64 kbps                |
| 4 | 3                         | 6                   | ≈96 kbps                |
| 5 | 4                         | 10                  | ≈128 kbps               |
| 6 | 5                         | 15                  | ≈160 kbps               |
| 8 | 7                         | 28                  | ≈224 kbps               |

CPU и память тоже линейны по N−1. Абсолютные величины из общего шаблона («менее 5% ядра», «30–60 МБ на инстанс») смешивают базовую стоимость стека WebRTC с ценой одного соединения — базовая платится один раз, каждое дополнительное соединение добавляет свой кодек и джиттер-буфер. Пока это не измерено на реальных устройствах, точных чисел здесь нет; **измерить нужно на N=6 и на самом слабом целевом устройстве**, потому что именно там меш упирается первым.

Практический потолок для меша на мобильных устройствах — ориентировочно 6–8 участников. Если Palette регулярно созваниваются большим составом, решением будет SFU, а это отдельная медиа-инфраструктура (mediasoup / Janus / LiveKit), а не доработка этого сервера.

## 3. Требования к сигнальному серверу

### 3.1 Что уже есть

| Требование                                                        | Состояние                                                                                              |
|--------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------|
| WebSocket (RFC 6455) поверх TCP                                    | есть, `GET /ws`                                                                                          |
| Аутентификация до апгрейда                                         | есть, но **временная и небезопасная** — `AuthService::authenticate` берёт steamId прямо из токена, без проверки |
| Личность соединения не подделывается клиентом                     | есть, steamId передаётся через `ParameterMap` апгрейда                                                  |
| DTO для `sdp_offer` / `sdp_answer` / `ice_candidate` / `call_hangup` | есть                                                                                                     |
| Маршрутизация                                                      | **есть**, `CallSignalService::relayToPeer` реально пересылает через `SignalTransport`                    |
| Проверка членства при маршрутизации                                | **нет** — открытый relay по `toSteamId`, `TODO` в `CallSignalService.cpp`, см. §3.6 и §7.6               |
| Реестр присутствия                                                 | есть, `ConnectionHub`                                                                                    |

### 3.2 TLS — обеспечивается не сервером

Общий шаблон предполагает WSS/TLS 1.3 на 443 порту в самом сигнальном сервере. **Здесь этого нет и не планируется в процессе:** сборка использует `oatpp::network::tcp::server::ConnectionProvider`, `oatpp-openssl` в `conanfile.txt` отсутствует, TLS в коде не упоминается. Сервер говорит обычным WS на `PICASSO_PORT` (по умолчанию 8000).

Следствия:

- WSS обязателен в продакшене и должен терминироваться обратным прокси (nginx / Caddy / Traefik) перед сервером.
- Прокси должен корректно проксировать апгрейд (`Upgrade`, `Connection`) и **не** резать долгоживущие соединения по таймауту простоя — WS-соединение живёт часами, а звонки в нём редки.
- Заголовок `Authorization` должен доходить до сервера без изменений: на нём держится вся аутентификация апгрейда.

### 3.3 Привязка только к IPv4

`ServerRunner` создаёт провайдер с `oatpp::network::Address::IP_4`. На IPv6-only мобильной сети клиент не достучится до сигнального сервера вообще — до всякого ICE. Если целевая аудитория сидит в мобильных сетях, это надо решать: либо поддержкой IPv6 на сервере, либо двойным стеком на прокси.

### 3.4 Производительность: почему «<10 КБ на соединение» здесь неверно

Общий шаблон даёт оценку «менее 10 КБ RAM на одно активное WebSocket-соединение». Она справедлива для событийного цикла. Этот сервер использует **блокирующий** API oat++, то есть поток на соединение, а с долгоживущими WS — поток на клиента.

Значит цена соединения — это стек потока. По умолчанию 8 МБ виртуальной памяти; фактический RSS кратно меньше, поскольку страницы выделяются лениво, но это всё равно на порядки больше десяти килобайт. Уменьшение размера стека потоков названо в [CLAUDE.md](../CLAUDE.md) как незакрытая задача, и для сотни-другой соединений на маленьком VPS оно обязательно.

Полезная нагрузка сообщений при этом действительно крошечная:

- SDP-оффер/ансвер: ~1–3 КБ;
- ICE-кандидат: ~150–300 байт, обычно 4–12 кандидатов на пир на пару.

### 3.5 Всплеск сигнального трафика при старте звонка

В меше объём сигналинга квадратичен. На старт звонка из N участников:

- SDP: N(N−1) сообщений (оффер и ансвер на каждую пару);
- ICE: примерно 8·N(N−1) сообщений при 8 кандидатах на сторону.

Для N=6 это порядка 30 SDP (≈30–90 КБ) и до 240 ICE-кадров (≈36–72 КБ) — суммарно около 70–160 КБ, приходящих **всплеском за несколько секунд**. Каждый кадр требует проверки членства.

Отсюда два требования, оба уже заложены в архитектуру:

1. Набор бесед пользователя кэшируется на сессии при подключении, а не запрашивается на каждый кандидат. Поход в базу на 240 кадров за пару секунд недопустим.
2. Исходящая очередь сессии ограничена, и ронять при переполнении можно **только** `ice_candidate`. Чат ронять нельзя никогда (сервер — SSOT), `sdp_offer`/`sdp_answer` и управляющие кадры звонка ронять нельзя тоже: потерянный оффер убивает установку сессии молча, и ничто его не повторит.

Уточнение к политике сброса ICE, которого не было в исходных требованиях: Trickle ICE избыточен, поэтому потеря части кандидатов переживаема, но нельзя терять **все** кандидаты одного пира и нельзя терять признак конца сбора. Разумная политика — ограничивать очередь на пир, а не глобально.

### 3.6 Маршрутизация: не pass-through — а сегодня именно pass-through

Формулировка «трансляция сообщений без модификации тела» верна только в части «тело не разбирается». Тело SDP и ICE сервер действительно не парсит. Но пересылать кадр только потому, что в нём указан `toSteamId`, нельзя: тогда любой аутентифицированный пользователь сможет слать произвольные нагрузки любому пользователю в обход членства в беседе, то есть сервер станет открытым релеем.

Требование: `CallSignalService` обязан убедиться, что **и отправитель, и получатель** состоят в `conversationId`, и только после этого пересылать. Поле `fromSteamId` проставляет сервер; присланное клиентом отбрасывается.

**Это требование сегодня не выполнено кодом**, не только не описано протоколом. `CallSignalService::relayToPeer` пересылает `sdp_offer`/`sdp_answer`/`ice_candidate`/`call_hangup` любому `toSteamId`, которого назовёт клиент, без единой проверки — ровно тот открытый релей, которого требование избегает. Это явно отмечено `TODO(roadmap step 4/5)` в `CallSignalService.cpp` и держится только на том, что аутентификация (§3.1) сама временная и не проверяет личность всерьёз. Закрывается вместе с шагом 4 дорожной карты, когда `ConversationRepository` перестанет быть заглушкой.

## 4. STUN и TURN

Роли независимы от сигнального сервера и в этом репозитории не реализуются — здесь только требования к ним.

### 4.1 STUN (RFC 5389)

Определяет внешний адрес клиента (кандидат `srflx`). Для разработки допустим публичный сервер вроде `stun:stun.l.google.com:19302`. Для продакшена лучше свой — публичный это внешняя зависимость в пути установки звонка.

### 4.2 TURN (RFC 5766 / 6156, например coturn)

Обязателен для гарантии соединения: при симметричном NAT (мобильные сети, корпоративные сети) прямой путь не строится, и остаётся релей (кандидат `relay`).

**Экономика релея в меше — это то, что общий шаблон недооценивает.** Оценка «40–60 kbps на активный разговор» относится к одной паре. При релее меша через TURN нагрузка на сервер:

| N | Пар | Полоса TURN, если релеятся все пары |
|---|-----|-------------------------------------|
| 2 | 1   | ≈64 kbps                            |
| 4 | 6   | ≈384 kbps                           |
| 6 | 15  | ≈960 kbps                           |
| 8 | 28  | ≈1.8 Mbps                           |

Числа даны для худшего случая (все пары через релей); на практике 80–85% пар соединяются напрямую. Но планировать канал надо от худшего, а не от среднего, и **один параллельный звонок на шесть человек в полном релее — это около мегабита исходящего трафика с VPS**. Для истории Free Tier с установкой одной командой на произвольный VPS это существенно: TURN может оказаться дороже самого сервера. Стоит явно решить, входит ли TURN в Free Tier или это ответственность self-host-пользователя.

### 4.3 Авторизация TURN — и чего для неё не хватает

TURN с постоянными общими учётными данными — открытый релей для всего интернета. Требуется механизм временных учётных данных (TURN REST API, Shared Secret HMAC-SHA1): сервер выдаёт клиенту логин вида `<timestamp>:<steamId>` и пароль как HMAC от него на общем секрете, срок жизни — минуты.

**Этого в текущем протоколе нет.** Ни один эндпоинт и ни один тип кадра не передаёт клиенту конфигурацию ICE-серверов. Пока это не добавлено, клиенту неоткуда взять ни адреса STUN/TURN, ни креды — а зашивать их в клиент нельзя, потому что при мультисерверной схеме у каждого сервера свой TURN. ## 5. Сетевая матрица портов

| Узел                    | Протокол  | Порт                                  | Назначение                            | Обязательность             |
|-------------------------|-----------|---------------------------------------|---------------------------------------|----------------------------|
| Сигналинг (этот сервер) | TCP       | `PICASSO_PORT`, по умолчанию **8000** | WS для чата и обмена SDP/ICE          | да                         |
| Обратный прокси (TLS)   | TCP       | 443                                   | WSS снаружи, обычный WS внутрь        | да для продакшена          |
| STUN                    | UDP       | 3478                                  | определение внешнего адреса           | да                         |
| TURN (управление)       | UDP / TCP | 3478                                  | аутентификация, выделение релея       | да для продакшена          |
| TURN (TLS)              | TCP       | 5349                                  | обход жёстких корпоративных фаерволов | рекомендуется              |
| TURN (релей)            | UDP       | 49152–65535                           | пересылка SRTP                        | да, если задействован TURN |
| Клиент P2P              | UDP       | динамический                          | прямой обмен SRTP/SRTCP               | да для меша без релея      |

Два отличия от исходной матрицы:

- **Порт сигналинга 8000, а не 8080.** Умолчание задано в `Config`, меняется через `PICASSO_PORT`.
- **TURN over TLS вынесен на 5349, а не на 443.** В исходной матрице и WSS, и turns стоят на 443, а это прямой конфликт: на одном IP один слушатель на порт. Развести можно либо разными адресами, либо мультиплексированием по ALPN на прокси. 5349 — штатный порт turns и путь наименьшего сопротивления; 443 для TURN имеет смысл добавлять отдельно и осознанно, ровно ради обхода фаерволов, которые пропускают только 443.

## 6. Качество канала

Метрики относятся к каналу между парой пиров либо между пиром и TURN. В меше их надо выдерживать **на каждой из N−1 связей** — деградация одной связи слышна как проблема с одним конкретным собеседником, а не как общий сбой звонка, и диагностировать это надо соответственно.

| Метрика           | Требование                                                |
|-------------------|-----------------------------------------------------------|
| Полоса на связь   | минимум 32 kbps, рекомендуется 64 kbps                    |
| Полоса на клиента | (N−1) × указанное выше, см. §2.5                          |
| RTT               | отлично < 150 мс, допустимо 150–300 мс, критично > 400 мс |
| Джиттер           | < 30 мс                                                   |
| Потери пакетов    | < 3%                                                      |

Opus с включённым FEC и PLC переживает 10–15% потерь, но это запас прочности, а не рабочая точка.

NetEQ компенсирует джиттер адаптивным буфером — ценой задержки. На высоком джиттере RTT и джиттер складываются в ощущаемую задержку, поэтому канал, проходящий по джиттеру, но лежащий на границе по RTT, на слух будет плохим.

## 7. Пробелы протокола, блокирующие RTC

Ниже — то, чего не хватает в текущем `EnvelopeDto`, чтобы меш заработал. Первые три блокируют реализацию, остальные закрывают дыры в поведении.

### 7.1 Некуда взять конфигурацию ICE-серверов

Клиенту нужны адреса STUN/TURN и временные учётные данные TURN. Ни в REST, ни в кадрах их нет, а зашивать в клиент нельзя: в мультисерверной схеме TURN у каждого сервера свой.

Нужен REST-эндпоинт, отдающий список ICE-серверов с кредами, живущими минуты. Запрашивать перед каждым звонком, а не при логине — креды короткоживущие.

### 7.2 У звонка нет идентификатора

`CallInviteDto` и `CallSignalDto` несут только `{conversationId, steamId}`. В меше звонок переживает входы, выходы и пересогласования, и опоздавший кадр от предыдущего звонка неотличим от кадра текущего. Нужен `callId`, проставляемый сервером при первом `call_invite` в беседе и присутствующий во всех кадрах звонка, включая SDP и ICE.

### 7.3 Присоединяющийся не узнаёт состав звонка

`peer_joined` сообщает об изменениях. Клиент, принявший приглашение в уже идущий звонок, не получает **начальный** список участников — а без него он не знает, кому слать офферы. В меше это обязательный шаг: N−1 соединений надо кому-то адресовать.

Нужен кадр или поле в ответе на `call_accept`, несущее текущий состав.

### 7.4 Не определено, кто из пары делает оффер

Если оба пира одновременно создадут оффер, получится glare, и его придётся разруливать откатом. Правило должно быть детерминированным и не требовать переговоров — например, «оффер делает тот, у кого steamId численно меньше». Это соглашение ничего не стоит зафиксировать сейчас и дорого чинить потом.

### 7.5 `toSteamId` не адресует устройство

Это самое неприятное из списка, потому что следует из уже работающего кода. `ConnectionHub` сознательно отображает один steamId в **несколько** соединений: клиент, открытый на телефоне и на десктопе, — это два соединения, и оба должны получать сообщения. `sendTo` рассылает всем.

Для чата это правильно. Для RTC — нет: `sdp_offer`, адресованный по `toSteamId`, придёт на оба устройства пользователя, оба ответят, и на один оффер вернутся два ансвера. Меш такого не переживёт.

Значит, RTC-кадры должны адресоваться не пользователю, а **конкретному соединению**. Нужен идентификатор соединения (или устройства), выдаваемый при апгрейде, попадающий в состав участников звонка и заменяющий `toSteamId` в маршрутизации SDP/ICE. Проверка членства при этом остаётся по steamId.

### 7.6 Членство в беседе — не то же самое, что участие в звонке

Проверка «оба состоят в `conversationId`» разрешает слать SDP любому участнику беседы, даже если тот не в звонке и никуда не звонил. Правильная проверка — «оба состоят в активном звонке `callId`», и она становится возможной после §7.2.

Важная оговорка: этот раздел описывает недостаток *целевой* проверки членства — она рассуждает так, будто проверка «оба состоят в conversationId» уже существует и её просто недостаточно. В работающем коде сегодня нет даже этого: `relayToPeer` не проверяет ничего (см. §3.6). Пока это не закрыто, вопрос «участие в звонке или в беседе» — следующий шаг после того, как вообще появится первая проверка.

## 8. Что это значит для клиента

Клиент общается не с абстрактным сигнальным сервером, а с этим протоколом. Ниже — форма кадров, которые он шлёт и получает; полная таблица типов в [SERVER.md §7.2](SERVER.md).

Исходящий оффер:

```json
{
  "type": "sdp_offer",
  "sdp": {
    "conversationId": "12",
    "toSteamId": "76561198000000001",
    "sdp": "v=0\r\no=- ... m=audio ..."
  }
}
```

`fromSteamId` клиент не заполняет — сервер проставит его сам, и присланное значение будет отброшено. Поле `toSteamId` подлежит замене на адрес соединения, см. §7.5.

Медиа-ограничения на стороне клиента — только аудио:

```kotlin
val mediaConstraints = MediaConstraints().apply {
    mandatory.add(MediaConstraints.KeyValuePair("OfferToReceiveAudio", "true"))
    mandatory.add(MediaConstraints.KeyValuePair("OfferToReceiveVideo", "false"))
}

val audioSource = peerConnectionFactory.createAudioSource(MediaConstraints().apply {
    mandatory.add(MediaConstraints.KeyValuePair("googEchoCancellation", "true"))
    mandatory.add(MediaConstraints.KeyValuePair("googAutoGainControl", "true"))
    mandatory.add(MediaConstraints.KeyValuePair("googNoiseSuppression", "true"))
    mandatory.add(MediaConstraints.KeyValuePair("googHighpassFilter", "true"))
})
```

ICE-серверы **не зашиваются в клиент**: при мультисерверной схеме у каждого сервера свой TURN, и креды короткоживущие. Конфигурация запрашивается у того сервера, которому принадлежит беседа, перед каждым звонком — как только появится эндпоинт из §7.1.

В меше `RTCConfiguration` применяется к каждому из N−1 PeerConnection, а не к одному: соединение создаётся на каждого участника, полученного из состава звонка (§7.3).
